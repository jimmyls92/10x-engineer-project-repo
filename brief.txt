Attempts 
Three attempts at this module submission. Attempts are counted per

Scenario 
The backend works, but nobody can understand it and nobody has planned what comes next. Good 
documentation and precise specifications are the difference between a project and a product. 
About “Provisional”. Two criteria here come back marked Provisional — meaning no problems so far, 
but they get looked at again at the end of Module 3. Your documentation still has to match your code 
after Module 3's feature work and refactoring. 
Tasks 
Task 2.1 — Comprehensive README 
Replace the basic README with a professional one: 
□ Project overview and purpose 
□ Features list 
□ Prerequisites and installation 
□ Quick start guide 
□ API endpoint summary with examples 
□ Development setup 
□ Contributing guidelines

Check it on a clean clone. Missing environment variables and dependencies are the usual failure. 
Task 2.2 — Docstrings across the codebase 
Google-style docstrings on every function and class: 
□ backend/app/models.py — all Pydantic models and fields 
□ backend/app/api.py — all endpoint functions with Args, Returns, Raises 
□ backend/app/storage.py — the storage class and all methods 
□ backend/app/utils.py — all utility functions, with examples where helpful 
Documented parameters, returns and exceptions must match what the code actually does. A docstring 
that restates the function name as a sentence does not meet the standard. 
Task 2.3 — API reference → docs/API_REFERENCE.md 
□ Every endpoint documented — including the PATCH endpoint you added in Module 1 
□ curl or fetch request examples for each 
□ Sample responses 
□ Error codes and response formats 
□ Authentication notes (even if “none” for now) 
Task 2.4 — Custom AI agent 
Create .github/copilot-instructions.md or .continuerules with: 
□ Coding standards specific to this project 
□ Preferred patterns and conventions 
□ File naming conventions 
□ Error handling approach 
□ Testing requirements 
Also required: docs/agent-effect-note.md — a short note showing one concrete instance where 
generated output changed because of this file. Show the before and after. Generic best-practice advice 
that would suit any project, with no evidence it affected anything, does not meet C2.3. 
Task 2.5 — Feature specifications 
Two specs in specs/. You will implement one in Module 3 and the other in Module 4, so both need to be 
genuinely implementable. 
specs/prompt-versions.md and specs/tagging-system.md must each contain: 
□ Overview and goals 
□ User stories with acceptance criteria 
□ Data model changes needed

□ API endpoints with request and response shapes 
□ Error conditions and edge cases — specified, not left implicit 
Every endpoint needs at least one acceptance criterion you could write a test from directly. “Handles 
input correctly” is not testable. “Returns 422 with a field-level message when tag is longer than 32 
characters” is. 
Time spent here has the highest return in the course. Vague requirements produce vague generated 
code, and you pay for it in Modules 3 and 4.
